## A09-Adapter-Re-Review

A09 bestätigte PASS für die zwei UI/API-Fixes aus CP-0289: Kostenarten erlauben nur ausdrücklich `true`/`false`, und Ressourceninitialisierung ist nach dem ersten Tagesereignis (Tag offen oder geschlossen) gesperrt. ## Bestätigter lokaler Browserpfad und MIME-Ursache

Read-only HTTP-Prüfung an Port 8031 bestätigte: `run.html`, `run.js` und Run-Abhängigkeiten antworten mit HTTP 200, aber ohne `Content-Type`. Der Portprozess ist ein temporärer Node-Staticserver, der Bytes direkt ohne MIME-Header streamt. Die ES-Module wurden deshalb vom Browser nicht als Module initialisiert; das erklärt den zuvor wirkungslosen Startklick. Es wurde keine Produktquelle geändert, um Serverkonfiguration zu überdecken.

A01 startete für die Funktionsprüfung einen temporären lokalen Staticserver auf `127.0.0.1:8032` mit `.js/.mjs` als `text/javascript; charset=utf-8`; dieser lieferte `run.js` mit HTTP 200 und korrektem Header. Im kontrollierten IAB funktionierten daraufhin Runstart, Tagöffnung, Anfragepostfach, explizite Testkalkulation/Angebotsabgabe (Preis 330 €, variable direkte Kosten 50 €, DB I 280 €; kein Posting) und Tagesabschluss.

## Neuer UI-Blocker und Folgeauftrag

Nach Tag 1 war „Nächsten Simulationstag öffnen“ deaktiviert, wenn kein `modules.product`-Stand existierte, obwohl die UI vor Tag 1 Ressourcen als optional bezeichnete. Ressourcen können nach dem ersten Event aus berechtigter Restore-/Integritätsgrenze nicht ergänzt werden. Somit gelangt ein Lauf ohne Initialisierung in eine Sackgasse.

A05 hat den Folgeauftrag, die gemeinsame Run-UI konsistent zu machen: ein operativer V3-Lauf erfordert vor dem ersten Tag eine explizite Ressourcenbasis ohne Defaults, oder eine klar getrennte Market-only-Route muss offen als nicht auftragsfähig gekennzeichnet werden. Bevorzugter Standard für die gemeinsame Run-UI ist notwendige Ressourceninitialisierung vor Tag 1. Keine fachlichen Ressourcenannahmen werden erfunden.
